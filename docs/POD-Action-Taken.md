## Plan for remaining (Partial / Not Done) items

Ordered quick wins first.

### Item 23 — User-friendly error messages (audit remainder) — Size: S
- **Scope:** Grep every remaining `res.status(...).json({ error: ... })`/`catch` block in `cirl.js` and `services/*.js` not already covered by `test/error-message-safety.test.js`'s representative routes, and confirm none echoes a raw driver/library exception message back to the client.
- **Affected files:** `cirl.js` (every route's catch block), `services/*.js` (any service that currently returns `err.message` upward instead of a fixed string).
- **Risk:** Low — this is an audit-and-patch pass over existing patterns, not new behavior; the fix shape (log the real error, return a fixed friendly string) is already established and tested.
- **Estimate:** S.

### Item 11 — Dedicated international accreditation monitoring — Size: S/M
- **Scope:** Decide whether "monitoring" means (a) a filterable view of all logged Accreditation-category achievements with a date/level field, or (b) a true status tracker (accreditation level, valid-until date, renewal milestone) distinct from a one-off achievement log entry. Likely (a) is the quick win; (b) would need its own collection/fields.
- **Affected files:** `views/administrator/admin_dashboard.ejs` (Achievements UI), `cirl.js` (`POST /api/achievements` and its GET routes), possibly a new `validUntil`/`level` field on achievement records if (b) is chosen.
- **Risk:** Low for (a); medium for (b) if it needs a new data shape and its own expiry/notification logic (would reuse the existing milestone-notification pattern already built for partnerships).
- **Estimate:** S for (a), M for (b).

### Item 28 — Report generation under every module (extend to Document Library and Requests) — Size: M
- **Scope:** Reuse Monitoring's existing `monitoringGenerateReport()`/`monitoringExportReport()` pattern (preview using the page's own current filters, export PDF/Excel) for the Document Library and Partnership Requests pages.
- **Affected files:** `views/administrator/documents.ejs`, `views/administrator/partnership_requests.ejs` (new buttons + preview modal, modeled on `views/administrator/monitoring.ejs:1021-1091`), `cirl.js` (a report-building endpoint per module, or a shared one parameterized by module+filters).
- **Risk:** Low-medium — the pattern and its PDF/Excel export plumbing already exist and are tested; the main work is wiring each module's own filter state into it.
- **Estimate:** M (two modules × UI + endpoint wiring).

### Item 1 — OCR cold-start latency (pool a warm worker across jobs) — Size: M
- **Scope:** Promote the per-job Tesseract worker (currently created and terminated once per `processImage`/`processPdf` call) to a small long-lived worker pool shared across jobs, removing the ≈1-7s `createWorker` cost on every single-page upload (multi-page jobs already amortize this within one job).
- **Affected files:** `services/ocrService.js` (`createReusableWorker`, `processImage`, `processPdf`, `runJob` — introduce a module-level pool with a max-idle-worker cap and a termination timer for when the app is quiet).
- **Risk:** Medium — concurrent jobs would need to either share a pool of N workers (simple, bounded memory) or queue when the pool is busy; needs a decision on N for this deployment's expected concurrency (likely 1-2, given "a single-instance capstone deployment" per the file's own existing comment).
- **Estimate:** M.

### Item 7 — College Dean: add an activity + upload documents — Size: M
- **Scope:** Extend `GET/POST /api/partnerships/:id/activities` (and its export) to also admit the College Dean for partnerships their college is actually a party to, or add a parallel Dean-facing endpoint/UI if Admin/Staff must keep final visibility/approval over Dean-submitted activities (needs a decision: can a Dean add directly, or does it need Admin/Staff review first, mirroring the College Request pattern already used elsewhere for Dean submissions?).
- **Affected files:** `cirl.js:1453-1508` (role gate + any new review/approval step), a new or extended view under `views/auth. personnel/` for the Dean to add an activity and attach documents (reusing the existing upload/OCR pipeline, same as College Requests already does).
- **Risk:** Medium — needs a product decision (direct-add vs. review-gated) before implementation; the underlying collection, upload pipeline, and PDF export already exist and would be reused, not rebuilt.
- **Estimate:** M.

### Item 29 — AI-based text extraction instead of Tesseract — Size: L
- **Scope:** A genuinely new capability: route scanned-document OCR through a multimodal AI model instead of (or as a fallback/comparison alongside) Tesseract, including prompt design for structured field extraction, cost/latency/accuracy evaluation against the current pipeline, and a decision on whether this replaces Tesseract outright or runs as an opt-in improvement.
- **Affected files:** `services/ocrService.js` (new extraction path alongside/replacing `ocrImage`/`processPdf`'s OCR branch), `services/extractionService.js` (field-extraction logic may change shape if the AI model returns structured fields directly instead of raw OCR text), new API-key/config plumbing (mirroring the existing Gemini integration's config and privacy-gate pattern in `services/aiInsightService.js`/`services/analyticsIntentService.js`).
- **Risk:** High relative to the others — a new paid external dependency, accuracy must be proven at least equal to the current Tesseract pipeline before any cutover, and it touches the one feature (document extraction) the whole upload pipeline depends on.
- **Estimate:** L.

**Proposed order:** 23 → 11(a) → 28 → 1 → 7 → 29.
